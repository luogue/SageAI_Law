# 合同审查引擎可执行项文档

## 1. 文档目标

本文档用于固化合同审查第二版的标准工作流，适用于后续各类合同审查清单的测试、问题记录、逻辑修正和封板验收。

执行目标不是重新设计审查清单，而是按统一标准完成：

- 测试材料准备
- 审查报告生成
- 风险项逐项核验
- 误判项修正
- 回归测试
- 封板确认

审查引擎只能输出风险提示、修改建议、法律依据和证据说明，不得输出裁判结论、胜负判断或责任判决。

## 2. 适用范围

本文档适用于已发布审查清单的合同类型，包括但不限于：

- 房屋租赁合同
- 买卖合同
- 赠与合同
- 技术合同
- 保证合同
- 后续新增或待测试的其他合同类型

每一类合同进入测试前，必须确认其审查清单已接入统一注册表，并可通过审查第二版接口加载。

## 3. 标准工作流

### 阶段一：前置确认

#### 3.1 确认合同类型

执行前必须明确本轮测试的合同类型，例如：

- `service`
- `guarantee`
- `technology`
- `deposit`
- `work_contract`

确认事项：

- 该合同类型是否已存在审查清单文件。
- 该合同类型是否已注册到统一清单加载机制。
- 前端下拉选项或接口参数是否能正确选择该合同类型。
- 合同类型名称、配置 key、前端显示名是否一致。

若合同类型未注册，不得进入测试阶段，应先完成数据层接入。

#### 3.2 准备测试材料

测试材料可以是：

- 官方示范文本
- 项目内已有测试合同
- 为该合同类型专门编写的简化模板

测试材料必须满足：

- 文件类型为 `.docx` 或 `.pdf`。
- 合同标题与所选合同类型一致。
- 正文包含该类合同的核心条款。
- 若为简化模板，应在报告顶部注明“测试材料为简化模板，部分缺失项可能源于模板简略”。

不得使用合同类型明显不一致的材料测试，例如用服务合同材料测试委托合同。

#### 3.3 确认通用规则

测试前必须确认以下三条通用规则已在该合同类型中生效。

第一，适用条件过滤机制：

- 特定场景审查点只在合同触发对应场景时执行。
- 未触发场景时标记为“不适用”。
- 不适用项不得计入高、中、低风险统计。

第二，证据实质性匹配规则：

- 命中原文必须实质覆盖审查点的法律要求。
- 不得只因出现表面关键词就判定通过或部分覆盖。
- 例如“通知”不能当然覆盖“催告留痕制度”，“押金返还”不能覆盖“征收拆迁处理”。

第三，通知类条款功能区分规则：

- 提前解除通知、催告通知、送达条款、交接通知不得混同。
- 审查点涉及通知、送达、催告时，应核对其具体法律功能。

若上述规则未生效，应先补规则，再执行正式测试。

### 阶段二：测试执行

#### 3.4 上传测试材料

在合同审查第二版页面执行：

1. 选择对应合同类型。
2. 上传测试文件。
3. 点击审查。
4. 等待报告生成。

也可以通过后端接口或测试脚本调用 `review_contract_v2` 执行同等测试。

#### 3.5 生成审查报告

审查报告应包含：

- 报告提示
- 风险总览
- 高、中、低风险数量
- 不适用项数量
- 每个审查点的覆盖状态
- 问题类型
- 命中原文
- 原文位置
- 系统判断理由
- 风险点描述
- 缺失的法律后果
- 建议条款示例
- 法律依据索引
- 人工复核状态和备注

若报告缺少证据条款、判断理由或法律依据，应视为报告不完整。

#### 3.6 初步判断报告质量

生成报告后先做快速质量判断：

- 报告是否完整生成。
- 合同类型是否识别正确。
- 高风险数量是否明显异常。
- 是否存在大量与合同类型无关的审查点。
- 是否存在不适用项被计入风险统计。
- 是否出现裁判式表述，如“应赔偿”“驳回请求”“判决结果”。

若发现大量跨类型误判，应优先检查适用条件过滤，而不是逐项调整风险等级。

### 阶段三：结果判定与封板

#### 3.7 逐项验证高风险项

对所有高风险项逐项核验：

- 是否属于该合同类型的核心履行障碍。
- 是否直接影响合同效力、履行、付款、交付、责任承担或权利实现。
- 是否因模板空白导致，而不是完全缺失。
- 是否本应属于不适用场景。
- 证据引用是否与审查点实质匹配。

高风险项必须做到“少而准”。封板时高风险项原则上不超过 5 项，且必须全部准确。

#### 3.8 检查通过项

通过项也必须抽查，重点看：

- 是否真的有正式合同条款覆盖。
- 命中原文是否与审查点相关。
- 是否把普通条款误当成专项条款。
- 是否把附件、使用说明、示范文本提示误当成正式约定。

通过项出现证据张冠李戴时，应修正证据实质性匹配规则。

#### 3.9 检查部分覆盖项

部分覆盖项应区分：

- 模板空白：合同已有条款框架，但金额、日期、比例、选项等未填写。
- 条款缺陷：合同已有约定，但法律要素不完整或责任边界不清。

示例：

- “押金人民币____元”属于模板空白。
- “违约金按合同金额 50% 支付，但未与实际损失挂钩”属于条款缺陷。

不得将模板空白误判为完全缺失。

#### 3.10 检查不适用项

不适用项必须满足：

- 合同中未触发该专项场景。
- 该审查点确实只服务于特定交易结构或特殊情形。
- 不适用项未计入高、中、低风险统计。
- 报告中能说明不适用原因。

常见不适用示例：

- 普通买卖合同中不适用试用买卖审查点。
- 委托开发合同中不适用技术转让、技术许可、技术咨询、技术服务审查点。
- 一般保证合同中不适用最高额保证期间审查点。
- 单一保证人合同中不适用共同保证份额和内部追偿审查点。

#### 3.11 整理修正清单

发现误判后，修正清单必须逐项记录：

| 字段 | 要求 |
|---|---|
| 审查点编号 | 例如 `GUA-10-02` |
| 当前状态 | 例如“中风险-完全缺失” |
| 问题原因 | 例如“单一保证人合同中不适用共同保证份额” |
| 修正动作 | 改为不适用、调整风险等级、修正证据、修改判断理由 |
| 适用条件 | 明确触发关键词或结构条件 |
| 验证方式 | 指定测试合同和预期输出 |

不得只写“优化一下”“误判”之类无法执行的描述。

#### 3.12 完成修正

修正时优先顺序：

1. 先改适用条件过滤。
2. 再改证据实质性匹配。
3. 再改风险等级。
4. 最后改展示文案。

不要用降级掩盖不适用问题。若审查点本身不应执行，应标记为“不适用”，而不是从高风险降为中风险或低风险。

#### 3.13 回归测试

每次修正后必须重新测试：

- 当前合同类型专项测试。
- 当前测试材料实际审查输出。
- 全量审查清单测试。

推荐命令：

```powershell
pytest backend\tests\test_<contract_type>_review_checklist.py -q
```

```powershell
$files = Get-ChildItem backend\tests -Filter 'test_*review_checklist.py' | ForEach-Object { $_.FullName }
pytest @files backend\tests\test_review_v2_house_lease.py backend\tests\test_review_v2_contract_registry.py -q
```

若后端服务已启动，修正完成后应重启后端并确认健康状态。

```powershell
Invoke-RestMethod -Uri 'http://localhost:8016/health' -TimeoutSec 5
```

#### 3.14 封板验收

满足以下条件后，方可确认该合同类型封板：

- 高风险项数量不超过 5 项。
- 高风险项全部准确。
- 不适用项未计入风险统计。
- 模板空白与完全缺失区分清晰。
- 通过项证据引用准确。
- 无明显跨类型审查点误判。
- 报告无裁判式输出。
- 专项测试和全量回归测试通过。

若高风险项超过 5 项，但经人工确认全部为真实、重大、必须修正的合同风险，可以记录例外说明后封板。

## 4. 边界风险与应对措施

| 风险点 | 描述 | 应对措施 |
|---|---|---|
| 合同类型匹配错误 | 系统可能将其他类型合同误判为测试对象 | 生成报告前确认文件名称、合同标题和所选合同类型一致 |
| 适用条件过滤未生效 | 本应标记为“不适用”的审查点被误判为风险项 | 检查不适用项数量，优先排查跨类型或专项场景审查点 |
| 证据张冠李戴 | 审查点引用的原文位置与审查内容不匹配 | 逐项检查命中原文是否实质覆盖该审查点的法律要求 |
| 高风险数量异常 | 高风险项超过合理范围，可能存在跨类型误判 | 先排查不适用过滤，再排查风险等级 |
| 模板空白误判为完全缺失 | 简化模板中的未填写项被当作无条款 | 区分“有框架但未填写”和“完全没有该条款” |
| 特殊场景误触发 | 合同中普通词语触发专项审查点 | 对专项场景使用组合条件，不只用单一关键词 |
| 通过项误判 | 普通条款被误判为覆盖专项审查点 | 增加证据实质性匹配或节点专属证据规则 |
| 裁判式输出污染 | 审查报告出现“应赔偿”“驳回”等裁判结论 | 保留输出安全检查，发现后立即修正报告生成逻辑 |

## 5. 交付检测标准

封板前逐项确认：

- [ ] 审查报告已完整生成。
- [ ] 合同类型与测试材料一致。
- [ ] 高风险项数量不超过 5 项，或已记录合理例外。
- [ ] 高风险项全部准确。
- [ ] 无“不适用”项被误判为高风险、中风险或低风险。
- [ ] 合同已覆盖条款被正确判定为“通过”。
- [ ] 通过项证据引用准确。
- [ ] 未覆盖项被正确标记为“模板空白”或“完全缺失”。
- [ ] 不适用项不计入风险统计。
- [ ] 报告中每一项均包含法律依据索引。
- [ ] 报告中每一项均包含修改建议或建议条款示例。
- [ ] 修正清单已整理完毕。
- [ ] 修正后专项测试通过。
- [ ] 修正后全量回归测试通过。
- [ ] 后端服务已重启并健康检查通过。

## 6. 标准修正动作字典

| 修正动作 | 适用场景 | 示例 |
|---|---|---|
| 改为不适用 | 合同未触发该专项场景 | 单一保证人合同不适用共同保证内部追偿 |
| 调整风险等级 | 审查点适用，但风险严重性偏高或偏低 | 自然损耗排除从中风险降为低风险 |
| 修正证据引用 | 命中原文与审查点不匹配 | 水电费条款不能覆盖第三方侵权分流 |
| 调整覆盖状态 | 条款有框架但未填写，或完全没有条款 | “押金____元”为模板空白，不是完全缺失 |
| 增加组合触发条件 | 单一关键词容易误触发 | “保证期间届满后 + 催收签字”才触发期间届满后签字效力 |
| 增加跨条款依赖 | 后置条款依赖前置条款成立 | 附义务赠与的救济依赖具体义务内容 |

## 7. Codex 执行模板

后续每一类合同测试可以按以下模板执行：

```text
1. 确认合同类型和审查清单是否已接入。
2. 找到或准备测试材料。
3. 运行审查并生成报告。
4. 记录风险总览：高/中/低/不适用数量。
5. 逐项核验高风险项。
6. 抽查通过项证据。
7. 检查不适用项是否合理且未计入风险统计。
8. 整理误判清单。
9. 按“适用条件 > 证据匹配 > 风险等级 > 文案”的顺序修正。
10. 补专项测试。
11. 跑全量回归测试。
12. 重启后端服务。
13. 输出最终结论：修正内容、测试结果、报告路径、是否可封板。
```

## 8. 封板输出格式

每类合同封板时，最终说明建议采用以下格式：

```text
已完成【合同类型】审查引擎测试与修正。

结果：
- 高风险：X 项，均准确。
- 中风险：X 项。
- 低风险：X 项。
- 不适用：X 项，未计入风险统计。

关键修正：
- 审查点 A：从“当前状态”改为“目标状态”。
- 审查点 B：修正证据引用。
- 审查点 C：增加适用条件过滤。

验证：
- 专项测试：通过。
- 全量回归测试：通过。
- 后端服务：已重启，健康检查正常。

结论：
该合同类型达到封板状态 / 尚需继续修正。
```
